01前提として知っておくべき3つの世界

Agentic AIシステムは「AI」「クラウド」「コード」の3つの世界が絡み合った構築物です。 まずこの3つそれぞれが何なのか、最低限の前提を揃えましょう。

1-1. AIの世界 ―LLMとは何か

LLM（大規模言語モデル）は、文章を入力するとそれに続く文章を確率的に予測するAIです。 OpenAIのGPTシリーズ、AnthropicのClaudeシリーズ、MetaのLlamaなどが代表例です。LLMは「事前学習」した知識しか持っていないため、社内文書や最新情報を扱うには工夫（RAGやツール連携）が必要になります。

LLMの呼び出し方

LLMは多くの場合APIで呼び出します。本案件では、AWS上のBedrock経由でClaude Sonnet 4.5を呼んでいます。

# Python: LLMを呼び出す最小コード
from strands import Agent
from strands.models.bedrock import BedrockModel

model = BedrockModel(
    model_id="us.anthropic.claude-sonnet-4-5-20250929-v1:0",
    max_tokens=10000,
    temperature=0.35,
)
agent = Agent(model=model, system_prompt="あなたは調達分析の専門家です")
response = agent("銅価格の動向を教えて")
print(response)

1-2. クラウドの世界 ― AWSとは何か

AWS（Amazon Web Services）は、サーバーやストレージ、データベース、AI機能を必要なときだけ借りられるサービスです。自前で物理サーバーを買う必要がなく、使った分だけ課金されます。本案件のシステムは100%AWS上で動いています。

AWSは200以上のサービスを提供していますが、Agentic AIで使うのはおおむね10〜20種類です。本資料では05章で1つずつ説明します。今は「Lambda＝関数を動かすサービス」「S3＝ファイル置き場」程度の理解でOKです。

02Agentic AIとは何か

「Agentic AI」と「チャットAI」は別物です。違いを明確にしておくと、後の設計が腑に落ちます。

定義

Agentic AIとは、目的を与えられたとき、必要な手段を自律的に選び・実行し・結果を統合して回答できるAIです。 単一のプロンプト応答ではなく、複数の手段（検索、計算、API呼び出し、データ照会）を組み合わせて、複数のエージェントを協調させて動きます。

従来チャットAIとの比較

観点従来のチャットAIAgentic AI

Agentic AIの5大構成要素

① LLM（推論エンジン）

会話を理解し、次の行動を決める頭脳。Claude、GPT、Llama等。本案件はClaude Sonnet 4.5。

② ツール（Tool）

AIが呼び出せる「腕」。RAG検索、API呼び出し、計算、SVG生成、グラフ描画など。関数呼び出しと呼ばれる仕組みでLLMから起動。

③ 知識基盤（RAG）

LLMが知らない情報をベクトル化して保存し、質問時に類似文書を検索する仕組み。社内ドキュメント活用の定番。

④ Orchestrator

複数Agentを束ねる司令塔。ユーザー質問を受け、適切なAgentに振り分け、結果を統合する。

⑤ 観測・状態管理

会話履歴・トレース・実行ログを保存し、何が起きたか追跡できるようにする層。

なぜ「複数Agent」にするのか 1つのLLMに全部やらせると、プロンプトが肥大化して品質が落ち、コストも増えます。「分解Agent」「検索Agent」「要約Agent」と役割分担すれば、各Agentのプロンプトは短く保てて、テスト・改修・差し替えがしやすくなります。マイクロサービスのAI版と考えると分かりやすいです。

03題材プロジェクト：調達向け情報検索エージェント

本ガイドの題材は、三菱電機 AXイノベーションセンター 基盤開発部向けに2026年3月に納品されたPoC案件です。 調達業務の担当者が自然言語で問い合わせると、AIが市況・サプライヤー・調達方針・サステナビリティの4領域を横断検索して根拠付き回答を返します。

ユースケース例

User Query 1 「銅素材の価格動向と将来の展望を教えて。」
User Query 2 「A社のサステナビリティ評価を、過去のSAQ回答とともに確認したい。」

裏側で何が起きるか

  1. UIで質問入力

    ブラウザで動くチャット画面（Next.js）にユーザが質問を打ち込み、送信ボタンを押す。

  2. 認証＆Backend経由でOrchestrator呼び出し

    UIからJWT付きでBackend (Lambda) のAPIを叩き、BackendがAgent層のOrchestratorを非同期で起動する。

  3. 問い合わせ分解

    Orchestratorがまず問い合わせAgentを呼び、質問をMECEな調査タスク（最大12個）に分解。

  4. 専門Agent並列実行

    分解されたタスクを、A2Aプロトコルで市況検索／サプライヤー検索／調達方針検索／サステナ検索の各Agentに送る。

  5. 各AgentがRAG検索

    各Agentがkb_retrieveツールで関連文書を取得。スコア付きで返す。

  6. 証拠十分性の自己評価

    結果を再度問い合わせAgentに渡し、「証拠は十分か」を点数評価。60点未満なら再分解→再検索。

  7. 要約Agentで統合

    十分性OKなら要約Agentへ。Markdown形式で「結論／根拠／注意点／出典」に整形。必要に応じてSVGチャートやMermaid図を生成。

  8. 結果をS3に書き出し

    Orchestratorが各ターンの会話履歴・実行状態をS3に書き込み、UIは3秒ごとにポーリングして結果を取得・表示。

リージョンを分けている理由

UI/Backendは東京（ap-northeast-1）、Agentはバージニア（us-east-1）で動かしています。 理由はAWSのAIサービス（Bedrock AgentCore、Knowledge Bases、最新Claudeモデル等）の多くがus-east-1で先行リリースされるからです。日本リージョンには遅れて来るため、PoC時点ではus-east-1で構築するのが定石です。

2リージョン構成の注意点 UI（東京）からAgent（バージニア）への呼び出しはネットワーク遅延が増えます。本案件ではBackendが非同期でAgent起動 → UIはS3経由でポーリングすることで遅延を吸収しています。同期APIで太平洋を越えると数百ms追加されるため、設計が必要です。

データフロー：1往復の完全な流れ

  1. ユーザー認証

    ブラウザがCloudFront経由でUIを取得。Cognito Hosted UIにリダイレクトし、ユーザがログイン。CognitoがJWTトークンを発行し、ブラウザのLocalStorageに保存。

  2. API呼び出し

    UIがPOST /api/chat/{Thread ID}を叩き、JWTをAuthorizationヘッダで送信。CloudFrontを経由してAPI Gatewayへ到達。

  3. JWT検証

    API GatewayのCognito Authorizerがトークンを検証。OKなら対応するLambda（chat-start-handler）を起動。

  4. Orchestrator非同期起動

    LambdaがAgentCore Runtimeの/invocation APIを非同期モードで呼び出し。即座にRun IDが返り、Lambdaは終了（数百ms）。

  5. Orchestrator内部処理

    Orchestratorが問い合わせAgent→各専門Agent→要約Agentと順に呼ぶ。各ターンごとにS3にtalk.jsonlとstatus.jsonを書き込み。

  6. UIのポーリング

    UIは3秒ごとにGET /api/runs/{Run ID}を叩き、S3のstatus.jsonを読みに行く。status: "complete"になったら最終結果を表示。

非同期パターンの重要性

AgentCore Runtimeは同期APIだと最大15分、非同期APIだと最大8時間まで実行できます。 Agentic AIの実行は数十秒〜数分かかることが多いため、同期APIだと先にタイムアウトしてしまうのです。 本案件では「Lambdaが非同期で投げる→S3で状態を共有→UIがポーリングする」という王道パターンを採用しています。 

# Backend Lambda (TypeScript): Orchestrator非同期起動
const client = new BedrockAgentCoreClient({ region: "us-east-1" });
const response = await client.send(new InvokeAgentRuntimeCommand({
  agentRuntimeArn: "arn:aws:bedrock-agentcore:us-east-1:xxx:runtime/orchestrator-xxx",
  runtimeSessionId: threadId,
  payload: JSON.stringify({ user_prompt: userMessage, history: [...] }),
  executionMode: "ASYNC",  // ★ 非同期モード
}));
return { runId: response.taskId };  // 即座にUIへ返す

05AWSサービス基礎 ― 1つずつ理解する

ここではAgentic AI構築で使うAWSサービスを1つずつゼロから説明します。Lambdaを知らない人でも理解できるよう、何なのか・なぜ必要か・どう使うかを順に整理します。

▶コンピューティング系

Lambda

Lambdaは「コードを1つの関数として動かすクラウドサービス」です。 従来は「サーバを買って→OSを入れて→アプリを動かす」必要がありましたが、Lambdaは関数のコードだけ書けば、リクエストが来たとき自動で起動・実行・停止してくれます。

  • 用途：本案件ではBackend APIの実装に9本のLambdaを使う（スレッド作成、ユーザプロンプト送信、状態取得など）
  • 言語：Node.js / Python / Java / Go など主要言語に対応
  • 料金：実行時間（ミリ秒）×メモリ量。アイドル時は無料
  • 制限：1回の実行は最大15分。それ以上は別の仕組み（Step Functions、AgentCore非同期等）が必要

API Gateway

API Gatewayは「APIの玄関」です。 ブラウザからのHTTPリクエストを受け、URLパスやメソッドに応じて適切なLambdaに振り分けます。認証チェック、IP制限、リクエスト数制限なども担います。

本案件では/api/chat, /api/runs/{id}などのエンドポイント定義をすべてAPI Gatewayで集中管理し、それぞれを対応するLambdaに紐付けています。

Bedrock AgentCore Runtime

AgentCore Runtimeは、Agentic AI向けの専用Lambdaのような存在です。 通常のLambdaは15分制限があるため、長時間動くAgentには向きません。AgentCore Runtimeは非同期実行で最大8時間動かせて、コンテナとして動くため、Pythonの大きな依存ライブラリも同梱できます。

▶ストレージ・データベース系

S3

S3は「クラウド版のファイルサーバ」です。 無制限にファイルを入れられて、HTTPで取り出せます。本案件では3つの用途で使っています：

  • UIホスティング：Next.jsをbuildした静的HTML/JS/CSSファイルを置く
  • 会話履歴保存：Orchestratorのtalk.jsonl、status.jsonを保存
  • RAGの原本格納：知識ベースのソースとなる文書ファイル

S3 Vectors

S3 VectorsはS3の新しい派生機能で、テキストの埋め込みベクトルを安く保存できるストレージです。 RAGで必須となる「ベクトル類似検索」のバックエンドとして使います。本案件では領域ごと（market/supplier等）に1つずつ作成しています。

Athena

AthenaはS3上のファイルに対してSQLを投げられるサービスです。 本案件では「ユーザーのスレッド一覧取得」で、S3に分散して保存された会話履歴JSONを横断的にSQL検索するのに使います。

▶AI/ML系

Bedrock

Bedrockは複数社のLLMをまとめて呼べるサービスです。 Claude（Anthropic）、Llama（Meta）、Titan（Amazon）等が選択でき、ベンダーロックインを避けつつLLMの能力を切り替えられます。

本案件はClaude Sonnet 4.5を使い、リージョン横断推論（Cross-Region Inference Profile）でUS全体のキャパシティを活用しています。

Bedrock Knowledge Bases

Bedrock Knowledge BasesはRAG（検索拡張生成）をマネージドで提供するサービスです。 ファイルをS3に置く→Bedrock KBが自動チャンキング・ベクトル化・インデックス構築→retrieve APIで類似文書を取得、という流れがワンストップで実現できます。

Bedrock Guardrails

Bedrock GuardrailsはAIへの不適切な入力／不適切な出力をフィルタリングする機能です。 本案件では「プロンプト攻撃」を高敷居値でブロックし、引っかかったら定型文を返す設定にしています。

AgentCore Memory

AgentCore MemoryはAgentの記憶を司ります。 STM（短期記憶）とLTM（長期記憶）の2階層を持ち、Strands Agentsから透過的に使えます。

▶認証・配信系

Cognito

Cognitoはユーザー認証の全部入りサービスです。ユーザープール（ID・パスワード保管庫）、Hosted UI（ログイン画面）、JWTトークン発行、二段階認証など、認証で必要なものが全て揃っています。

本案件はHosted UIを使い、Emailによる二段階認証を必須にしています。ユーザがログインに成功するとJWTが発行され、UIはこれを各APIに付けて送信します。

CloudFront

CloudFrontは世界中のエッジサーバから素早くコンテンツを配信するCDNです。 S3に置いたNext.jsのファイルをCloudFront経由で配信し、API Gatewayへのアクセスも一旦CloudFrontを通すことで、すべての通信に一貫したIP制限・SSL証明書を適用しています。

WAF

WAFはWebアプリケーション用のファイアウォールです。 本案件では「許可されたIPアドレスからしかアクセスできない」設定にしており、不正アクセスをブラウザレベルで遮断します。

SES

SESはAWSのメール送信サービスです。 本案件ではCognitoの二段階認証メールを送るために使います。新規アカウントは「サンドボックスモード」で送信先制限がかかるので、本番利用時は解除申請が必要です。

# market_search_agent/tools/kb_retrieve.py（概要）
from strands import tool
import boto3

bedrock_agent = boto3.client("bedrock-agent-runtime", region_name="us-east-1")

@tool(name="kb_retrieve", description="市況Knowledge Basesから関連文書を取得")
def kb_retrieve(query: str, top_k: int = 10, metadata_filter: dict = None):
    response = bedrock_agent.retrieve(
        knowledgeBaseId="KB_ID_MARKET",
        retrievalQuery={"text": query},
        retrievalConfiguration={
            "vectorSearchConfiguration": {
                "numberOfResults": top_k,
                "filter": metadata_filter or {},
            }
        }
    )
    return [{
        "text": r["content"]["text"],
        "source": r["location"],
        "score": r["score"]
    } for r in response["retrievalResults"]]
実装上の注意点 Bedrock KBのExcel/Word/PDF自動解析は精度が十分でないため、前処理でテキスト抽出と章分割を行ったmdファイル＋メタデータをデータソースに使う方が結果が安定します。チャンクサイズは「やや大きめ（最大8kトークン）」に設定し、後段Agentが必要部分のみ抜き出す方針です。

08プロンプト設計の作法

Agentic AIシステムの「品質」を決めるのは、コードよりもプロンプト設計です。本章では本案件で使われている実プロンプトの構造と工夫を解説します。

システムプロンプトとユーザープロンプト

  • システムプロンプト：Agentの恒久的な役割設定。「あなたは市況検索の専門家で、必ず出典付きで返答する」のような指示。
  • ユーザープロンプト：その都度の質問。ユーザー質問が上位、Agent間ではOrchestratorからの依頼。

本案件の問い合わせAgentシステムプロンプト（抜粋）

# 問い合わせAgent: 役割定義
あなたは調達業務の分析エキスパートです。
ユーザーの質問を受け取った場合は Mode 1 でタスクに分解し、
タスクと検索結果を受け取った場合は Mode 2 で十分性を判定します。

## Mode 1: タスク分解
- 出力は必ず JSON: {"tasks":[{"task":"...","weight":0.3}]}
- task は日本語、一問一答形式、「〜を教えて」で終わる
- 最大12タスク、weight合計1.0
- 分解順序: 判定基準 → 核心事実 → 補足（背景/比較/市場）→ 最新性

## Mode 2: 十分性判定
- 出力は必ず JSON: {"enough": true/false, "reason":"..."}
- 合計スコア 60点以上で enough = true
- 不足理由を具体的に書く

## 制約
- 三菱電機の価値観（信頼/品質/技術/倫理/環境）を踏まえる
- アイビー・ケース・システムの思考フレームワークを使う
- 出力以外の説明文は禁止

要約Agentシステムプロンプト（抜粋）

## 出力フォーマット（必須）
- 必ず日本語Markdown
- 出力は必ず「## 結論」から始める
- 構造: 結論 / 根拠 / 注意点 / 出典
- 絵文字禁止
- 「以下に〜を記載します」のような前置き禁止
- タスク分解の話は出力に含めない
- Agentエラーへの言及禁止

## 可視化
- 意思決定に最も役立つ図を1つだけ選ぶ
- 利用可能: svg_chart_tool / svg_bubble_chart_tool / svg_stat_map_tool / mermaid
- グラフ種別: bar / line / area / scatter / stacked_bar / pareto /
            waterfall / radar / bubble / stat_map_japan / stat_map_world

プロンプト設計の7つの原則

  1. 役割を明示する

    「あなたは○○の専門家です」と立場を固定。LLMの応答の一貫性が高まる。

  2. 出力形式を厳密に指定

    JSONなら「JSON以外を出力するな」とまで書く。Markdownなら見出しレベルまで指定。

  3. 禁止事項を明示

    「前置き禁止」「絵文字禁止」「謝罪禁止」など、ユーザー体験を損なう応答を明示的に止める。

  4. 例（Few-shot）を入れる

    具体的な入力例と望ましい出力例を1〜3組プロンプトに含める。応答品質が大きく上がる。

  5. 段階的に考えさせる

    「まず分解、次に評価、最後に統合」など順序を明示。CoTの効果。

  6. 不確実なときは「分からない」と言わせる

    「証拠が不十分なら推測せず『記載なし』と返す」と明示。ハルシネーションを抑える。

  7. テスト用ケースで継続改善

    本番でうまくいかないケースを集め、システムプロンプトとFew-shotに反映していく。

  2. ルートユーザでログイン

  3. 請求アラートを設定

  1. IAMユーザ作成

  2. 権限ポリシーをアタッチ

  3. MFA有効化

    多要素認証を必ず有効化。AWSコンソールへのログイン時に1回パスワード＋ワンタイムコード。

11-3. Bedrockモデルアクセス申請

Bedrockは初期状態ではどのモデルも使えません。明示的に有効化する必要があります。

  1. us-east-1へ切り替え

    右上のリージョン表示を「US East (N. Virginia)」へ。本案件のAgent層はus-east-1で動かす。

  2. Bedrockコンソールへ

    サービス検索で「Bedrock」を開く。左メニュー「Model access」。

  3. 使うモデルにチェック

    必要なモデル（Claude Sonnet 4.5、Claude Haiku、Titan Embeddings v2 など）にチェックを入れて「Request model access」。

  4. 承認を待つ

    Anthropic製は即時、他は数時間〜1日。承認後Bedrockから呼び出し可能になる。

  5. Cross-Region Inferenceの有効化

    本案件はus.anthropic.claude-sonnet-4-5-...を使っているが、これはCross-Region Inference Profileで、複数リージョンのキャパシティを束ねる。これも同じModel access画面で有効化。

14-4. execute.py 中核ロジック（イメージ）

class StrandsOrchestrator:
    async def run(self, thread_id, user_prompt):
        history = self.load_history(thread_id)

        # Step 1: 問い合わせAgentで分解
        decomposition = await self.agent_call_processor.call(
            "inquiry", {"mode": "decompose", "query": user_prompt}
        )
        tasks = decomposition["tasks"]

        # Step 2: 各タスクを適切な専門Agentに振り分けて並列実行
        agent_results = []
        for task in tasks:
            target = self.select_agent(task)  # Orchestratorプロンプトで判定
            result = await self.agent_call_processor.call(target, task)
            agent_results.append({"task": task, "result": result})
            self.storage.append_talk_log(...)  # 都度S3書き込み

        # Step 3: 問い合わせAgentで十分性判定
        eval_result = await self.agent_call_processor.call(
            "inquiry", {"mode": "evaluate", "results": agent_results}
        )
        if not eval_result["enough"]:
            # 不足なら再分解＋再検索（再帰）
            return await self.run(thread_id, user_prompt + f"\n追加: {eval_result['reason']}")

        # Step 4: 要約Agentで統合
        summary = await self.agent_call_processor.call(
            "text-summary", {"query": user_prompt, "results": agent_results}
        )

        # Step 5: 完了状態をS3に書き込み
        self.storage.write_status({"status": "complete"})
        self.storage.append_talk_log({"source": "assistant", "message": summary})
        return summary

import { APIGatewayProxyHandler } from "aws-lambda";
import { BedrockAgentCoreClient, InvokeAgentRuntimeCommand } from "@aws-sdk/client-bedrock-agentcore";
import { z } from "zod";

const bodySchema = z.object({
  message: z.object({
    role: z.literal("user"),
    content: z.string(),
    createdAt: z.string().datetime(),
  }),
});

const agentcore = new BedrockAgentCoreClient({ region: "us-east-1" });

export const handler: APIGatewayProxyHandler = async (event) => {
  const threadId = event.pathParameters!.threadId!;
  const body = bodySchema.parse(JSON.parse(event.body!));
  const userId = event.requestContext.authorizer!.claims.sub;

  // AgentCore非同期起動
  const resp = await agentcore.send(new InvokeAgentRuntimeCommand({
    agentRuntimeArn: process.env.ORCHESTRATOR_ARN!,
    runtimeSessionId: threadId,
    payload: JSON.stringify({ thread_id: threadId, user_prompt: body.message.content, user_id: userId }),
    executionMode: "ASYNC",
  }));

  const runId = `run_${threadId}_${resp.taskId}`;
  return { statusCode: 200, body: JSON.stringify({ runId }) };
};

async function pollRunStatus(runId: string) {
  while (true) {
    const resp = await fetch(`/api/runs/${runId}`);
    const data = await resp.json();
    if (data.status === "complete") return data.result;

from opentelemetry import trace
tracer = trace.get_tracer("a2a-server")

async def handle_request(req):
    with tracer.start_as_current_span("inquiry") as span:
        span.set_attribute("user.id", req.user_id)
        span.set_attribute("thread.id", req.thread_id)
        result = await process(req)
        span.set_attribute("tokens.used", result.tokens)

20トラブルシューティング

構築時によく遭遇する問題と対処を整理します。

20-1. CDKデプロイ系

症状原因と対処
cdk bootstrapが失敗IAM権限不足。AdministratorAccessを一旦付与。aws configureのリージョンも確認。
ACM証明書が発行されないRoute 53のNSレコードが正しく登録されていない／DNS未浸透。dig NS your-domain.comで確認、伝播待ち。
CloudFrontがアクセスエラーWAFのIP制限に自分のIPが含まれていない。cdk.jsonのwafAllowedIpAddressesを確認。
2FAメールが届かないSESがサンドボックスモード。解除申請が必要。
「Resource is not authorized」エラーLambda実行ロールに必要権限が無い。CDKのGrant文を確認。

20-2. Agent系

症状原因と対処
Bedrock呼び出しが「AccessDenied」Bedrockコンソールでモデルアクセス申請をしていない。「Model access」画面でチェック。
「ThrottlingException」が頻発Bedrockのキャパシティ上限。Cross-Region Inferenceを使う、Quotaを引き上げ申請。
Agentが返事を返さない15分の同期API制限を越えている。非同期APIに切り替え。
AgentCardが取得できないAgentCoreがlocalhostアドレスを返している。A2A SDKのラッパで変換処理を追加（本案件のorchestrator実装参照）。
LLM出力がJSONとして壊れているプロンプトに「JSON以外を出力するな」と強く明示。response_format指定も検討。

20-3. RAG系

症状原因と対処
retrieveが空配列を返すデータソースが同期されていない。KBコンソールの「Sync」を実行。
関連性の低い文書が返るチャンクサイズが大きすぎる／メタデータが不適切／前処理が雑。前処理を再検討、チャンキング戦略を見直す。
Excel/PDFが正しく取り込まれないBedrock KBの自動解析は精度が低い。テキスト抽出 → md化を前処理で行う。
メタデータフィルタが効かないRECORD_BASED_STRUCTURE_METADATA形式で投入していない。フォーマット確認。

20-4. UI系

症状原因と対処
ログイン後リダイレクトが繰り返すCloudFrontの「/api以外をUIにredirect」設定でループ。callbackパスを除外。
JWTが「expired」エラー1時間程度の有効期限切れ。Cognitoのリフレッシュトークンで更新する処理を追加。
ストリーミング応答が表示されないCloudFrontのキャッシュ設定がストリーミングを阻害。Cache-Control: no-cacheを付ける。
Mermaid図がレンダリングされないmermaid.contentLoaded()が呼ばれていない。useEffectでcontent変更を監視。
